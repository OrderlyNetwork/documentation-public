---
title: "Error Response"
description: "Format and example of WebSocket error responses, including the client ID mapping pattern."
---

Error responses follow the same format as successful responses, with `success` set to `false` and an `errorMsg` field explaining the issue. You can use the `id` field to map the error response with the corresponding request.

```json
{
  "id": "clientID7",
  "event": "subscribe",
  "success": false,
  "ts": 1614141150601,
  "errorMsg": "invalid symbol PERP_BTC_USDC"
}
```

## Common error messages

| Error message                        | Description                                      |
| ------------------------------------ | ------------------------------------------------ |
| `invalid symbol <symbol>`            | The requested symbol does not exist              |
| `invalid topic <topic>`              | The requested topic is not supported             |
| `auth failed`                        | Authentication failed due to invalid credentials |
| `missing required parameter <param>` | A required parameter is missing                  |

## Broker stream errors

The [Broker Data Stream](/build-on-omnichain/websocket-api/broker-stream#errors-and-reconnecting) returns command error details in `data` rather than `errorMsg`. Connection-level rejection, including an unrecognized broker admin account, may omit the client request ID and event before closing the connection. See the broker guide for the response example and access checks.
